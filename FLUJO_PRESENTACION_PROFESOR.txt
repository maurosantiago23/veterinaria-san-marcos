para la Clinica Veterinaria San Marcos.
Queremos destacar que la plataforma web conserva el mismo diseno visual y la
misma identidad que presentamos en la Unidad 2; lo que incorporamos para esta
entrega son importantes mejoras tecnicas y funcionales en la integracion con el

La solucion esta construida sobre una arquitectura Cloud de tres capas reales:
1. Frontend SPA reactivo en React 19 con Vite, servido en el puerto 5173 de AWS EC2.
2. Backend en Java 21 LTS con Spring Boot en el puerto 8080 de AWS EC2, con

3. Base de Datos Oracle Autonomous Database (ATP 19c) en Oracle Cloud,
   modelada en Tercera Forma Normal (3FN) y conectada mediante mTLS con
   Oracle Wallet sin exponer credenciales en la red."

BLOQUE 2: BASE DE DATOS ORACLE CLOUD Y MODELO 3FN (02:00 - 05:00)
--------------------------------------------------------------------------------
Pantalla:
Mauro cambia a la Pestana 3 (GitHub / schema.sql) o muestra el diagrama DER
en la documentacion.

Voz: Gabriel
"Para la persistencia de datos implementamos Oracle Cloud Autonomous Database
en la region sa-valparaiso-1, estructurada bajo 5 tablas relacionales:
- USUARIO: Manejo de clientes, vendedores y administradores con roles y claves cifradas.
- CATEGORIA: Alimentos, Farmacia, Accesorios y Servicios Medicos.
- PRODUCTO: Catalogo de insumos clinicos y atenciones veterinarias.
- BOLETA: Encabezado de la venta con folio, fecha, total y usuario asociado.
- DETALLE_BOLETA: Lineas de cada compra con cantidad y precio unitario historico.

En cuanto a normalizacion, destacamos la Tercera Forma Normal (3FN): en la tabla
DETALLE_BOLETA guardamos el precio unitario y subtotal al momento de emitir la
boleta. Si un producto cambia de precio en el futuro en la tabla PRODUCTO, las
boletas historicas no sufren ninguna alteracion, eliminando dependencias transitivas.

Ademas, la comunicacion entre la maquina virtual de AWS EC2 y Oracle Cloud no
utiliza contrasenas en texto plano, sino una conexion mTLS bidireccional basada
en certificados mediante la Oracle Wallet (cwallet.sso)."

BLOQUE 3: MICROSERVICIOS BACKEND SPRING BOOT Y SWAGGER (05:00 - 08:30)
--------------------------------------------------------------------------------
Pantalla:
Mauro pasa a la Pestana 2 (Swagger UI en AWS EC2: http://<IP_EC2>:8080/swagger-ui/index.html)
y ejecuta las peticiones en vivo.

Voz: Mauro
"En el backend aplicamos una arquitectura modular orientada al dominio dentro
de Spring Boot (Package-by-Feature):
- cl.duoc.vet_sanmarcos_backend.productos
- cl.duoc.vet_sanmarcos_backend.usuarios
- cl.duoc.vet_sanmarcos_backend.ventas

Esto nos permite mantener una separacion estricta de responsabilidades entre
servicios, sin sobrecargar la memoria de la maquina virtual AWS EC2 levantando
3 maquinas virtuales Java separadas.

Demostracion en vivo en Swagger:
1. GET /api/v1/productos:
   Mauro ejecuta 'Try it out' y 'Execute'.
   Muestra la respuesta 200 OK con los productos activos en Oracle ATP 19c,
   destacando la diferencia entre insumos fisicos y servicios con cupos.
2. POST /api/v1/auth/login:
   Mauro envia credenciales de prueba (admin@veterinaria.cl / 1234).
   Muestra el token JWT generado por Spring Security con su rol asignado.
3. POST /api/v1/boletas:
   Mauro explica la transaccion atomica con la anotacion @Transactional en
   BoletaService. La creacion de la boleta, la insercion de sus detalles y el
   descuento de stock en PRODUCTO ocurren en una sola operacion. Si no hay
   stock suficiente o falla la conexion, Spring aplica un rollback automatico
   completo, evitando boletas huerfanas o descuadres de inventario."
